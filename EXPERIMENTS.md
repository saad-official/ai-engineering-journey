| 2026-09-17 | exp-003 | What do temperature and top_p actually do to output variance, and is temperature 0 deterministic? | `labs/03-params`, Groq `openai/gpt-oss-20b`, 2 prompts (open-ended naming vs a closed factual question) x temps 0.0/0.7/1.2 x 5 runs, plus seed=42 at 1.2 and top_p 1.0 vs 0.1 at temp 1.0; variance = distinct count + mean pairwise difflib word similarity over all C(5,2) pairs; 45 calls | **Variance is a property of the prompt, not just the temperature.** Creative prompt: 1 distinct / sim 1.000 at temp 0.0, 5 distinct / 0.260 at 0.7, 5 distinct / 0.155 at 1.2. Factual prompt: **1 distinct / 1.000 at all three temperatures** - temp 1.2 changed nothing. The 0.0->0.7 step is the big one (sim drop 0.74); 0.7->1.2 adds only 0.105 more. `seed=42` at temp 1.2 did not pin output but narrowed it (5 distinct/0.155 -> 3 distinct/0.627). `top_p=0.1` at temp 1.0 collapsed output to 1 distinct / 1.000 - the same string temp 0.0 produced. Hidden reasoning was **84-95% of all output tokens** (e.g. 319 of 340). First run was void: `MAX_TOKENS=256` gave `finish_reason='length'` on 22/45 calls because reasoning ate the whole budget. | Choose temperature by whether the output is parsed or read, and verify on the actual prompt - a factual prompt is insensitive to it, so testing the knob on the wrong prompt teaches nothing. Most of the control lives between 0.0 and 0.7. Never rely on temp 0 for reproducibility: store outputs, don't re-derive them. Don't set temperature and top_p together - they reach the same place by different mechanisms. For reasoning models, budget `max_tokens` for the hidden chain of thought or measure nothing at all; and their ~90% invisible-token overhead is a real argument against them for cheap high-volume classification. | `labs/03-params/NOTES.md` |
| 2026-09-20 | exp-004 | What does a hand-written tool-calling loop actually cost, and does the request envelope grow with a system message and tool schemas (open question from exp-002)? | `labs/04-tools`, Groq `openai/gpt-oss-20b`, temp 0, no framework. 6 loop sections (happy path, two tools, tool raises, unknown tool, malformed JSON arguments, max-iteration guard) with the full message array and `usage.prompt_tokens` printed per step; plus the same user message sent 5 ways (bare / +system / +1 schema / +other schema / +both) at max_tokens=1 | **The envelope grows a lot.** Bare user message 80 tokens; +system +72; +`get_weather` schema +155; +`calculate` +140; +both **+268**. Since both (+268) < the sum of each alone (+295), the cost decomposes into a **one-off 27-token framing block** emitted when any tool is present, plus **128** and **113** per schema. Re-sent on EVERY loop step. **The model never batched tool calls**: asked to compare two cities it fetched them one per turn, so section B took 4 model calls and 2094 billed input tokens for one question. All four failure paths recovered without a crash: unknown tool refused on the name before argument parsing; `JSONDecodeError` position handed back and the model reissued correctly; tool error text listing valid cities let the model adapt in one turn; the max-iteration guard fired and returned `final_text=None` rather than a half-answer. 13 calls, $0.000831. | A tool loop is not N small calls, it is one growing call: step count is a budget line, and every extra tool is ~120 tokens on every step, so tool inventories should be scoped per task rather than attached wholesale. One-call-per-item behaviour doubles that again, which makes batching inside a single tool (accept a list of cities) a real design lever. Return errors to the model as data - it recovers - but refuse unknown tools on the name alone, before parsing: the dispatch table is an authorisation boundary. Never execute a tool call arriving with `finish_reason='length'` - truncated arguments can parse and be wrong. | `labs/04-tools/NOTES.md` |
